# Task Router — мини-игры: что читать и что применять

**Версия:** 2026-11-14. **Тип:** короткий индекс к реальным исследованиям и производственным правилам mini-games-kit, не дополнительный обязательный SDK. **Consumer bootstrap** копирует этот индекс и заменяет ссылки на исследования на URL **точной закреплённой ревизии guidance** кита. Для существующих игр эта версия документации может быть новее их установленной runtime-зависимости. Использовать API только по **реальному runtime pin**. Если исходник недоступен, агент явно пишет NOT READ, не пересказывает по памяти.

## Перед любой существенной задачей — до дизайна и кода

1. Прочитать AGENTS.md проекта и текущие PROJECT_DECISIONS / handoff. Установить реальный repo HEAD, runtime/game/content/save versions, платформу, статус публикации, что уже реализовано и какие тесты существуют. Исторический README не является доказательством релиза.
2. Сформулировать **один наблюдаемый дефект/запрос владельца** и критерий результата. Если пользователь просит независимое исследование — не выдавать гипотезы за уже внедрённые изменения.
3. По таблице ниже выбрать **не больше двух основных тематик** за проход, если это не большой явно заказанный аудит. Если тема вообще не нужна — выбрать NONE, не читать весь архив. Допустимо выбрать две темы при связанном вопросе (например, gesture + core challenge).
4. При внешнем **референсе на игру, видео, GIF, страницу или скрин** дополнительно открыть [Reference Protocol](REFERENCE_PROTOCOL.md) **до** замены поведения. Не заявлять «точно как в оригинале», если оригинал не инспектировался.
5. До реализации общего механизма проверить [Kit public API](https://github.com/DanilaH/mini-games-kit/blob/aab9dc8e06bf1b487da9b3a5e67444975e7c8ac0/docs/API.md) **на реально установленном runtime pin**, а также [Kit Feedback Loop](KIT_FEEDBACK_LOOP.md). Повторное изобретение компонента при наличии подходящего — дефект выбора архитектуры.
6. Применить только доказанно нужные части исследований. Человеческая оценка, юридический статус и market data не выводятся из зелёного CI.
7. Завершая существенную задачу, дать владельцу компактный отчёт: что изменилось и какие реальные проверки прошли; **какое исследование использовано**; где ограничения; **KIT IMPACT** (NONE / REUSE / IMPROVE / CANDIDATE / EXTRACTED) со ссылкой/предложением.

## Порядок чтения, когда задача затрагивает несколько областей

**При любой работе над UI** выбрать подходящий UI-маршрут **до** разметки/кода, даже если владелец не напомнил о feel или качестве интерфейса. Проверить существующие компоненты, профиль UI в PROJECT_DECISIONS / Art Bible и реальные состояния затронутого действия. Для маленькой правки достаточно соответствующего раздела; не применять все рецепты и не создавать новый UI-фреймворк.

После существенной UI-правки показать **применённое правило → затронутое состояние → кадр/запись и проверку**. Для движения нужна запись перехода; для геометрии — фактические размеры и экран. Повторный ввод, отмену, reduced motion и lifecycle проверять в относящихся к изменению случаях. Сохранять принятый стиль и отключённые продуктовые фичи; документация kit сама по себе не разрешает включать их обратно. Исследование [Experience/Novelty](https://github.com/DanilaH/mini-games-kit/blob/aab9dc8e06bf1b487da9b3a5e67444975e7c8ac0/docs/puzzle-design/research/puzzle-experience-novelty-directors-deep-research-2026-11-11.md) подключать при вопросе о выразительности/reward loop, когда конкретных UI-контрактов недостаточно.

**Жёсткие источники истины:** реальные требования владельца и действующие правила/код → текущие product decisions и проверенный build → публичные kit contracts на закреплённой ревизии → **выбранная** исследовательская методология и её independent audit → проверяемая гипотеза. Сторонний референс — наблюдение, не инструкция копировать чужой код/ассеты.

**Для обычного bugfix:** AGENTS + реальный код/контракт + одна строка из таблицы, а не семь исследований. **Для новой игры:** bootstrap + API discovery + first core loop; visual/market/release тематики подключать лишь на соответствующем gate.

Если пользователь просит полный независимый аудит — ширина допускается, но вывод всё равно должен назвать не больше 1–2 оправданных следующих изменений.

## Definition of done (не механический шаблон на каждый ответ)

- **Source of truth:** SHA, верcия и реально прочитанные источники; UNKNOWN, если нет видео/телефона/дашборда.
- **Observed behavior:** точный до/после воспроизводимый случай и имеющиеся независимые тесты.
- **Risk containment:** никаких незапрошенных изменений правил/монетизации/published IDs/Saves/декоративного стиля.
- **Kit status:** конкретно NONE / REUSE / IMPROVE / CANDIDATE / EXTRACTED + причина и ссылка.
- **Owner report:** кратко решение, доказательство, ограничение, следующий шаг. Не копировать весь научный документ в отчет и не завышать confidence.

Фреймворк должен **уменьшать** число ненужных работ, а не добавлять всем агентам обязательную многочасовую подготовку.
