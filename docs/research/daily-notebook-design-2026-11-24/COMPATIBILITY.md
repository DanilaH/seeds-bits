## 2. Идентичность поля

**Все существующие `book-v1-1…2400` сохраняют поля, сертификаты и ID.** Нельзя вставлять или сортировать записи внутри `notebook-extra.json`: ID вычисляется по позиции. Нынешние `daily-v1-YYYY-MM-DD` продолжают разрешаться в прежний результат алгоритма для своей даты. Нельзя поменять makePuzzle/hash и оставить старый ID как будто поле прежнее.

Новые тетради получают собственное пространство, например `book-v2-links-1…24` и `book-v2-shift-1…24`. Поле и content revision фиксируются в каталоге. Тематическая QA-витрина старых эталонов использует старые ID и не дублирует done/награду. Незавершённая сессия общая для всех входов. Для решённой задачи сохраняется штатный replay с новой attempt/session и текущим сбросом hints; новая попытка не создаёт повторного права на семечки.

Для новой daily возможен `daily-v2-YYYY-MM-DD`, связанный с неизменяемой записью принятого банка. Отдельно хранится **назначение даты**: дата → task ID + content revision + digest. Новая редакция банка не меняет уже назначенную запись. Если требуется исправить опубликованное поле, это отдельный versioned repair со своей миграцией, а не молчаливая перегенерация.

Не использовать content hash как новую глобальную платёжную идентичность: исторические daily/book разных режимов сохраняют действующие права. При этом у ежедневки право на её обычную награду привязано к **одному календарному дню** независимо от версии, чтобы не возникла повторная выплата v1→v2 за тот же день.

## 3. Сохранение и обновление

Рекомендуется **wire version 7** для новой структуры. Существующий FutureProgress уже различает более новый формат. При реализации проверить весь путь старой версии до UI: неподдерживаемый прогресс не должен сбрасываться или перезаписываться. Пробой только reader эту защиту до UI не доказал.

Миграция v6→v7 сохраняет active, boards, histories/Undo, hints, done, attempts, wallet, daily-series, темы и оплаченные/полученные права. Для существующих daily-сессий, выполненных дат и попыток восстановить назначение на соответствующий v1; из migrated done восстановить уже использованное право награды за calendarDay. Никакая миграция не должна заново выплачивать награду или импортировать кнопку paused help. Если запись неоднозначна, сохранять известный действующий v1-статус, а не генерировать другой пазл на ту же дату.

Назначение новой задачи и создание её сессии сохраняются атомарно до публикации игрового экрана; сбой durable-записи не оставляет нарисованную новую задачу с незафиксированной identity. Завершение и аналитическое событие фиксируются однажды для данной attempt после успешного сохранения; награда — при ещё не использованном праве. Повтор callback/перезапуск той же attempt не увеличивает счётчики. Штатное новое прохождение уже решённой задачи по-прежнему может учитывать ещё одно завершение попытки, но не вторую выплату семечек.

## 4. Календарь, архив и офлайн

Пусть **T** — будущая дата включения, выбранная при выпуске. В этой исследовательской работе дата не назначена и calendar entries не изменены.

Порядок разрешения дня:

1. Уже сохранённое назначение/сессия/завершение побеждает любой новый manifest. Применить старую доску и историю.
2. Для даты раньше T использовать v1, даже если пользователь прежде её не открывал. Архив не получает иное поле после обновления.
3. Для допустимой даты ≥T, покрытой проверенным включённым manifest, назначить фиксированное новое поле.
4. Для непокрытой даты использовать прежний детерминированный v1 как **обычную резервную задачу** и сохранить это назначение. Не называть её подтверждённой тематической постановкой. Следующий обновлённый банк не заменяет такой уже назначенный день.

Первые 28 новых записей встроены в приложение и доступны офлайн. После их окончания календарь не блокируется. Следующие порции можно доставлять обычным обновлением данных приложения; сервер/CMS/удалённая генерация для этого этапа не нужны. Если manifest содержит некорректный digest/proof, сборочный валидатор не выпускает такой банк; runtime не должен исполнять неподтверждённый вариант под прежней identity.

Смена суток не заменяет начатое поле. Игрок может закончить вчерашнюю задачу как архивную, затем открыть сегодняшнюю. Текущий смысл серии сохраняется: завершение **сегодняшней даты сегодня**. Доступность архива с 2025-01 и запрет будущих дат остаются. Использовать нынешний локальный календарь приложения, не вводить UTC-переход из-за исследовательских дат.

Трофей считает уникальные завершённые даты месяца, пороги **7 / 14 / все дни месяца**. В новом/старом смешанном месяце не учитывать один день дважды. Серия и её wallet-награды сохраняют текущую семантику (1 на третий день, 3 на каждом седьмом); это дополнительные подсказки, не семечки. Обычная задача даёт семечки по текущей формуле и только один раз за дату.

## 5. Все точки входа должны разрешать одну задачу

Рекомендуется небольшой чистый parser/resolver с метаданными `kind`, `calendarDay` либо `collectionId/position`, exact puzzle и revision. Он переиспользуется существующими экранами и подсистемами. Не размножать независимые `startsWith`/`slice` с новой версией по main.ts.

| `src/notebooks.ts` | Название, размер, страница, следующая задача; прежние 100 томов |

## Воспроизведение исследовательского probe

Node24, checkout с закреплённым commit или точный снимок перечисленных файлов. Пример:

```bash
SEEDS_CONTENT_REPO=/absolute/path/to/seeds-bits \
node docs/research/daily-notebook-design-2026-11-24/integration-probe.mjs
```

По умолчанию вывод в `test-results/daily-notebook-design/integration-probe.json`; `SEEDS_CONTENT_OUTPUT` меняет каталог, `SEEDS_CONTENT_SNAPSHOT` выбирает hash-verified исходный снимок вместо `git show`. Снимок использован в проведённом прогоне. Source manifest фиксирует байты и ревизию; новый продуктовый код отсутствует. **KIT IMPACT — CANDIDATE QA:** эти сценарии можно обобщить после фактической реализации и приёмки.
